# Publishing and project evidence

This repository contains three independently releasable artifacts: the Python
distribution, the operator container, and the Helm chart. The versions currently
present in source are development metadata, not evidence that any artifact has
been published. Check the intended registry or package index before advertising
availability.

## Release model

```{mermaid}
flowchart LR
  S[Source commit] --> P[Python package version]
  S --> I[Container tag and digest]
  S --> H[Helm chart version]
  I -->|values.image tag or digest| H
  P -. optional library use .-> U[Python consumers]
```

Version each artifact for changes to its own public contract:

* **Python:** update `[project].version` in `pyproject.toml`, build with
  `python -m build`, inspect the wheel/sdist, and publish them with the package
  index's trusted-publishing workflow. A package release need not imply a new
  chart release.
* **Container:** build for the supported platforms from `Dockerfile`, tag with
  an immutable release version, push, and record the registry digest. Prefer a
  signed image and provenance/SBOM generated by the chosen public registry
  workflow. Never infer a successful push from a local tag.
* **Helm:** update `version` in `charts/model-fleet-operator/Chart.yaml` for the
  chart and `appVersion` plus `values.yaml`'s image tag when the default
  application changes. Run the checks below, then use `helm package`. Publish
  the resulting archive to an OCI registry (or chart repository) and verify it
  by pulling it into a clean directory.

Keep a release record containing the source commit, all three versions, image
digest, chart digest, test logs, and changelog. Releases may share a version for
convenience, but do not have to. Use a release candidate first when CRD or
Kubernetes compatibility needs deployment validation. Publishing credentials,
registry coordinates, and signing identities belong in the public project's
release automation—not in this repository.

Example preparation (these commands build locally; they do **not** publish):

```bash
python -m pip install build
rm -rf dist && python -m build
docker build -t model-fleet-operator:${IMAGE_VERSION:?set-image-version} .
helm package charts/model-fleet-operator --destination dist
```

## Relationship to `agentic-kubernetes-platform`

Model Fleet Operator is independently installable with its chart on any
supported cluster that supplies the documented Gateway API/Cilium and KEDA
prerequisites. It does not require the sibling `agentic-kubernetes-platform`
repository, its agents, or its infrastructure modules.

The sibling platform can use Model Fleet as its workload control layer: agent
services submit model inference and training intent; Model Fleet reconciles
standard Deployments, Services, Jobs, routes, and scalers; the platform continues
to own cluster, Kafka, storage, identity, observability, and node capacity. Join
the projects through documented Kubernetes and JSON-RPC/gRPC interfaces and pin
each repository/artifact independently. Avoid source-directory imports or an
assumption that both release trains advance together.

```{mermaid}
flowchart TB
  A[Agentic Kubernetes Platform] -->|CRs and versioned service contracts| M[Model Fleet Operator]
  M --> K[Standard Kubernetes resources]
  K --> C[Cluster capacity and networking]
  A --> X[Kafka, storage, identity, observability]
  M -. optional integrations .-> X
```

## LinkedIn-ready technical narrative

> Model Fleet Operator turns inference, training, and immutable dataset intent
> into standard Kubernetes resources without introducing a proprietary runtime.
> It keeps pod autoscaling separate from node-capacity ownership, so the same
> workload API can fit local, cloud, and bare-metal clusters. The project is
> independently packaged while also composing with an event-driven agent
> platform through Kubernetes and versioned service contracts.

Evidence-backed capability bullets:

* Reconciles `InferenceService`, `TrainingRun`, and `Dataset` resources into
  Deployments, Services, Jobs, Cilium `HTTPRoute`s, and optional KEDA scalers.
* Supports explicit workload intent, scale-to-zero triggers, GPU fit classes,
  exact dataset-version checks, ServiceAccount allowlists, and Secret references.
* Provides optional durable Kafka commands, bounded Slack operations and App
  Home, Prometheus metrics, a Grafana dashboard, Hubble network panels, and
  MLflow hooks.
* Includes unit tests with coverage enforcement, multi-profile Helm checks,
  warning-as-error Sphinx builds, examples, and Terraform validation paths.

These bullets describe implemented source and tests. They do not claim a public
package/chart/image release, a production deployment, measured scale, cost
savings, reliability, or cloud-provider certification.

## Reproducible evidence capture

Create a directory named for an immutable commit (or `uncommitted` before the
first commit). Capture tool versions and preserve command exit codes:

```bash
set -o pipefail
EVIDENCE="evidence/$(git rev-parse --verify --short HEAD 2>/dev/null || echo uncommitted)"
mkdir -p "$EVIDENCE"
{ python3 --version; helm version --short; kubectl version --client; } \
  2>&1 | tee "$EVIDENCE/tool-versions.txt"
.venv/bin/pytest 2>&1 | tee "$EVIDENCE/pytest.txt"
make helm-lint 2>&1 | tee "$EVIDENCE/helm.txt"
helm template model-fleet charts/model-fleet-operator --set profile=kind \
  >"$EVIDENCE/model-fleet-rendered.yaml"
make docs-build 2>&1 | tee "$EVIDENCE/sphinx.txt"
```

The commands above are **local verification**: tests use fakes/mocks, Helm lint
and render do not contact a cluster, and Sphinx proves documentation builds. They
do not prove that controllers, external services, GPUs, routes, or telemetry
work in a deployment. Record the commit, command, UTC timestamp, environment,
and exit status with every artifact; review rendered YAML and remove credentials,
tokens, internal hostnames, account IDs, and user data before sharing.

### Deployment evidence users must capture

After installing into a non-sensitive test cluster, capture evidence rather than
turning expected behavior into a claim:

```bash
kubectl get inferenceservices,trainingruns,datasets -A -o yaml \
  >"$EVIDENCE/custom-resource-status.yaml"
kubectl get deployments,services,jobs,scaledobjects,httproutes -A \
  >"$EVIDENCE/generated-resources.txt"
kubectl describe inferenceservice -n models <name> \
  >"$EVIDENCE/inference-status.txt"
kubectl describe trainingrun -n models <name> \
  >"$EVIDENCE/training-status.txt"
```

Use an example appropriate to the cluster and retain its final `.status` phase,
ready replicas or Job result, generated child resources, and a successful request
through the route. A local kind echo example is not GPU inference evidence.

For optional integrations, capture separately:

* **Slack App Home:** screenshot the Home tab after `app_home_opened`, plus a
  redacted bot log and the installed manifest revision. Show inventory/action
  behavior; never expose tokens, user IDs, or private channel content.
* **Grafana:** export or screenshot the dashboard with time range, namespace,
  workload, data source, and collection time visible. “No data” is not success;
  identify which optional exporters were installed.
* **Hubble:** save redacted `hubble observe` output (or Hubble UI evidence) for
  the example request, including verdict and source/destination, and correlate
  its timestamp with the request. This proves observed traffic, not payload
  correctness.

Publish local-check logs and deployment evidence under distinct headings. If no
cluster evidence was captured, say **“deployment not verified”**. Screenshots
alone are supporting evidence; pair them with versions, timestamps, commands,
and machine-readable status wherever possible.
